🔬 Research Toolkit: Staged Workflow & FulltextCheckpoint

Interactive logic prototype demonstrating state transitions across Discovery, Zotero Ingestion, UCL Fulltext Checkpoint, and NotebookLM Sync.

Question Under Test (Issue #5)

What should the CLI interface and state contract look like for separating paper discovery & Zotero insertion from NotebookLM synchronization, allowing the user to inspect Zotero and verify UCL/OA full-text PDFs before upload?

Guided Walkthroughs (Test Scenarios)

Scenario 1: UCL Proxy & Connector Duplicate (User's Case)
Scenario 2: All Open Access (Automatic Flow)
Scenario 3: Partial Resolution & Force Sync

Scenario 1 Description: Papers are discovered and inserted into Zotero. One paper is non-OA (paywalled). The Checkpoint halts, prints UCL EZproxy link. The user clicks and saves via Zotero Connector, creating a duplicate item with full PDF. The toolkit reconciles the duplicate and uploads cleanly.

Scenario 2 Description: All papers retrieved are Open Access (e.g. ArXiv or Nature OA). FulltextCheckpoint passes automatically with 0 manual intervention.

Scenario 3 Description: 8 papers found, 6 have PDFs, 2 remain unavailable. User decides not to manually hunt down the remaining 2, running `sync-notebook --allow-partial`.
